# Declare the data the SDK collects

This page lists what the SDK sends to Pulsate, when it sends it, and which
call controls it. Use it to fill in the App Store privacy questions and the
Google Play Data safety form, and to see what stops collection.

For the calls themselves, see [Update the user profile and privacy](user-profile.md)
and [Set up location and geofences](location.md).

## 1. What the SDK sends to Pulsate

| Data | When it is sent | How the app controls it | Platform |
|---|---|---|---|
| App and device details: app version, operating system version, platform, language, time zone, bundle identifier or package name, SDK version | At session start, and in every user update | No call. The SDK sends them whenever a session runs | Both |
| Android build details: build type, minimum and target SDK levels, battery bucket, do-not-disturb state, background-restriction state | At session start, and in every user update | No call | Android |
| Device identifier: a random identifier the SDK generates for the install | At session start, and in every user update | No call | Both |
| Push token: the APNs token on iOS, the Firebase token on Android | At session start, and in every user update | The push setup in [Set up push notifications on iOS](ios-push-setup.md) and [Set up push notifications on Android](android-push-setup.md) | Both |
| Permission states: location, background location, notifications, in-app messages | At session start, and in every user update | The operating system grants, and `setPushEnabled` and `setInAppEnabled` for Pulsate's own preferences | Both |
| The user alias | At session start | `startSession(alias)` | Both |
| Profile fields: first name, last name, email address, phone number, age, gender | With the next user update the SDK sends | `updateFirstName`, `updateLastName`, `updateEmail`, `updatePhoneNumber`, `updateAge`, `updateGender` | Both |
| Privacy level | In a request of its own, within about sixty seconds | `setPrivacy` | Both |
| Custom attributes and custom events | Attributes with the next user update; events when the SDK sends them | `createAttribute`, `incrementAttribute`, `decrementAttribute`, `createEvent`, `createEvents`, `forceAttributeSync` | Both |
| Feed opens and the unread count | When the feed opens, and when the count is read | `showFeed`, `getFeedUnreadCount` | Both |
| Location: latitude and longitude, and geofence crossings | See [Location](#location) below | `setLocationEnabled`, and the operating system's location permission | Both |

The identifier is generated by the SDK. iOS stores it in the keychain and
Android stores it in the SDK's own database. Neither platform reads the
advertising identifier.

The feed is a web page Pulsate hosts. Opening it identifies the app, the
alias and the device to Pulsate. Reading the unread count also sends any
pending profile and attribute changes first.

### Location

The SDK needs the operating system's location permission on both platforms.
Location reaches Pulsate inside the session-start request and the user
update, as a latitude and longitude pair.

- iOS: the SDK starts Core Location when `setLocationEnabled(true)` is called.
  Core Location then delivers a fix after the device moves 1000 metres by
  default, at the best accuracy the device offers. The SDK shortens that
  distance when many geofences are nearby. Each fix is stored on the device, and
  Pulsate is told about geofence crossings.
- Android: collection is on by default. The permission alone lets the SDK
  collect, until `setLocationEnabled(false)` is called. The SDK requests no
  continuous updates. It reads the last known location from memory, from its own
  database, and then from Google Play services, at the moment it needs one.
  Geofence crossings are reported when Google Play services reports them.

## 2. Declare the data on the App Store

Apple asks which data types the app collects. Map the rows in step 1 to
Apple's categories using
[Apple's app privacy details](https://developer.apple.com/app-store/app-privacy-details/).

The `PULPulsate` framework the package pins ships a `PrivacyInfo.xcprivacy`
privacy manifest. It declares no tracking and no tracking domains. It lists
six collected data types: product interaction, coarse location, precise
location, performance data, crash data, and user ID.

> [!IMPORTANT]
> The framework's manifest does not list the profile fields the app sets.
> Declare the name, email address, phone number, age and gender yourself when
> the app calls the `update*` functions.

The React Native package ships no privacy manifest of its own. Its native
code calls none of Apple's required-reason APIs, so it adds no reason for you
to declare. The framework's manifest declares the one required-reason API the
native SDK uses, `NSPrivacyAccessedAPICategoryUserDefaults`, with reason
`CA92.1`. See Apple's
[privacy manifest files](https://developer.apple.com/documentation/bundleresources/privacy-manifest-files).

## 3. Declare the data on Google Play

Google Play asks the same question in the Data safety form. See Google's
[Data safety form guidance](https://support.google.com/googleplay/android-developer/answer/10787469).

| Data the SDK sends | Data safety category |
|---|---|
| Latitude and longitude, geofence crossings | Location |
| First name, last name, email address, phone number, age, gender | Personal info |
| The user alias | Personal info, user IDs |
| The device identifier, the push token | Device or other IDs |
| Custom attributes, custom events, feed opens, the unread count | App activity |
| App version, operating system version, build details, battery bucket | App info and performance |

## 4. Stop collection and delete data

- On Android, `setLocationEnabled(false)` stops location collection. The SDK
  stores the choice at once, sends it about a minute later, and stops
  geofence monitoring then.
- On iOS, `setLocationEnabled(false)` records the choice and stops nothing on
  the device. Geofences stay monitored, and crossings are still reported to
  Pulsate with the device's location. That lasts until the user logs out or
  Pulsate sends the device no geofences.
- Removing the operating system's location permission stops fixes on both
  platforms, whatever the setting says.
- `setPrivacy('unsubscribed')` records that the user does not want Pulsate
  campaigns. It does not stop the SDK sending session and device data.
- `setPushEnabled(false)` and `setInAppEnabled(false)` stop Pulsate messages.
  They do not stop collection either.
- `logout()` ends the session for the user. The device is logged out locally
  whichever way the promise settles. The stored alias is cleared, and on
  Android the in-app and notification state with it. On iOS the privacy level
  belongs to the device, so it survives `logout()` and applies to the next
  user on that device.
- The device identifier survives `logout()` on both platforms. On iOS it is
  held in the keychain, which outlives an app reinstall.

The SDK has no call that deletes a user's stored data from Pulsate. Delete a
user from the Pulsate dashboard.

## Verify

1. In Xcode, archive the app, then open **Generate Privacy Report** from the
   Organizer. The report lists the `PULPulsate` framework's collected data
   types and its `NSPrivacyAccessedAPICategoryUserDefaults` reason.
2. Call `setLocationEnabled(false)`, then `isLocationEnabled()`. It resolves
   `false`.
3. In the Pulsate dashboard, open **Users** and search for a test alias. The
   user shows the profile fields the app set, and no others.
